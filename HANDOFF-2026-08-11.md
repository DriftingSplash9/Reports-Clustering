## 3. Phase 0 is largely answered — start by confirming, not investigating

The plan is right that the 60-second load is not a camera problem. I believe the
dominant cause is already identified, and you can confirm it in one reading rather
than spending a session on instrumentation.

**`WARMUP_TICKS = 400` in `src/components/InfluenceGraph.tsx`.** Inside `runFit()`:

```js
for (let i = 0; i < WARMUP_TICKS; i++) fg.tickFrame()
```

That is 400 full force-simulation ticks over ~770 nodes, executed **synchronously
inside a single frame**, on the main thread, before the first useful render. The
UI shell has already mounted by then, which is exactly the symptom Thomas
describes: menus first, graph a minute later. `runFit` is called from `useFrame`
when `!fitted.current`, so nothing meaningful is drawn until it returns.

Corroborating measurement: when I drove the app headlessly on 2026-08-10 I had to
wait ~25 seconds after `networkidle` before the scene was settled enough to
screenshot, on a sandbox CPU. On a slower machine, or with the corpus grown, a
minute is entirely consistent.

**What to check before accepting this:**
1. Time `runFit()` directly — wrap the warmup loop in `performance.now()` and log
   it. If it is tens of seconds, that is your answer.
2. Confirm the data path is not the problem: `buildGraph`, `validate` and
   `disclosureByReport` all run in `useMemo` at App level and are single-pass over
   ~770 nodes and ~830 edges. They should be milliseconds. Measure rather than
   assume, but expect them to be innocent.
3. Note `fitted.current` is reset whenever `spreadApplied` changes, so **moving
   the Cluster spread slider re-runs the whole 400-tick warmup**. If Thomas has
   been touching that slider, he has been paying the cost repeatedly.

**Why the warmup exists** (do not delete it blindly): the comment says "Settle
before measuring, so the framing is not chosen from a tangle." The fit measures the
cloud radius to place the camera *and* now to scale the nodes. Both need a settled
layout. The fix is therefore not "delete the warmup" but "render during it" — tick
across frames, show the graph while it settles, and re-fit once when it converges.
That also fixes the `spread` slider stall for free.

## 4. The camera/legibility problem was different from the diagnosis, and is fixed

Worth reading because it is the clearest example in this project of measuring
instead of reasoning.

Thomas said he could not see nodes and edges until he adjusted the zoom. The
standing hypotheses were dim-opacity and drop-lines. Both were wrong. Rendering the
app headlessly and measuring the actual layout gave:

- connected cloud radius ≈ **1,407** world units
- fit camera distance ≈ **7,984**
- therefore one screen pixel ≈ **4.2** world units
- `radiusFor()` returned **2.2 to 8** world units, chosen when the corpus was ~120
  nodes

**So the smallest node was 1.0 pixel across and the largest 3.8.** Nothing was
broken; the constants had been outgrown. Fixed by making the visual radius
proportional to the measured cloud radius, with the collision radius deliberately
left alone so the layout cannot chase its own tail.

**The harness that found it is reusable and you should use it early** whenever
Thomas reports something visual:
- Chromium is at `/opt/pw-browsers/chromium`; do not run `npx playwright install`.
- Install playwright in `/tmp`, not in the repo — installing it into the repo
  breaks module resolution.
- Launch with `executablePath: '/opt/pw-browsers/chromium'` and the swiftshader
  args.
- **Wait ~25s after `networkidle`** before screenshotting (see §3 for why).
- To A/B a constant: **start a fresh dev server on a fresh port per variant.**
  Vite's watcher silently ignored `sed -i` edits to `src/lib/view.ts` and three
  "different" screenshots were the same build.
- **Never use search + flyTo to set up a comparison shot** — the camera lands
  differently each run and you end up measuring camera drift. Click a node at a
  fixed pixel after the fit; the layout is deterministic so the pixel is stable.

## 5. Phase 2 contradicts a decision Thomas made on 2026-08-10 — raise it before building

This is the most important thing in this handoff.

The plan's Phase 2 proposes continental repulsion plus nation affinity. **Thomas
was offered essentially this on the morning of 2026-08-10 and declined it**, after
I measured the graph and put three options to him. His words:

> "lets not fuck with it, if the are close because the countries and economies and
> whatnot are close then so be it"

The measurement behind that decision still stands, and Phase 2 needs to be argued
against it rather than around it:

- The corpus is **not** two clusters sitting near each other. Canada and the US are
  **the same connected component** — 288 nodes at last count (CA 125, US 58, NZ 27,
  INT 24, ZA 12, and a long tail). The EU family is a separate 153-node component.
  Roughly a third of all edges cross country lines, mostly through international
  framework hubs.
- So there is no latent structural separation to amplify. Any continental
  repulsion is **adding** a spatial claim the edges do not make.
- There is a documented rule this breaks. `InfluenceGraph.tsx` around line 78:
  *"every connected node's position is decided by its edges and nothing else,
  which is the position rule."* The isolated-node shelf is explicitly justified as
  not breaching it, because having no edges is a fact about the edges.

**This does not mean Phase 2 is wrong.** Thomas is allowed to change his mind, the
goal has since been restated as legibility *for other people*, and "nothing is
sacred" is in the plan. But the next agent should put the contradiction in front of
him explicitly rather than quietly implementing a force he rejected yesterday. If
he re-approves it, the plan's own guard rails are the right ones: soft, ablatable,
never overriding documented edges, never touching authority.

Two related decisions already made, which the plan partly re-opens:

- **Collapsible clusters: approved** (his answer was "yes!"), with the size of a
  collapsed group being its single highest-authority member, explicitly not a sum.
- **Community detection: declined** — "keep it simple." I inferred that to mean
  collapse along the existing `SCOPE_GROUPS` country families instead of computing
  Louvain communities, and I flagged that inference to him as unconfirmed. It is

## 6. Phase 3's headline item has a known trap

The plan's Phase 3 item 1 is Built-from / Feeds-into producing "little or no
visible change." That is real, and I spent several rounds on the adjacent question
yesterday. Save yourself the repeat:

**Dimming is not the lever.** `applyFocus()` works correctly — a console probe
confirmed `meshes=585 lit=54 dim=531 focus=true`, with materials being mutated as
intended. But measured over the canvas region, changing `DIM_NODE_OPACITY` from
0.34 to 0.15 moved mean scene luminance by nothing (17.455 → 17.455, 177 differing
pixels out of ~575,000). A probe forcing *every* node to `opacity 0,
emissiveIntensity 0` moved luminance only from 13.6 to 10.6 — meaning the
unfocused nodes were already contributing almost no light and essentially all of it
comes from the ~54 focused ones.

So if the focused chain needs to stand out more, **the change is on the lit side**
— raise the focused emissive, or give the selection its own treatment. Do not
approach it by dimming the rest further; there is nothing left to take away. The
constants are currently 0.15 / 0.03, which is marginally more correct and made no
visible difference.

Phase 3's actual open question is therefore narrower and better posed than the plan
states: *what visual channel distinguishes upstream from downstream?* Today the
focus set is a single undifferentiated "lit" state — `computeFocus` returns one
node set and one edge set, with `focusBuiltFrom` / `focusFeedsInto` only changing
which nodes enter it. There is no encoding that says "this one is upstream of your
selection and that one is downstream." That is the thing to design.

The plan proposes retargeting the pulse animation from publication rate to the
transmission / reference-period quantity. Thomas was asked exactly this and said
**hold**:

> Q9: "Pulses driven by transmission rather than publication rate — go or hold?"
> Answer: "ok" to the recommendation, which was **hold until reference_period

The reason: `reference_period` is on roughly 46 of 830 edges. An honest
transmission-driven pulse shows nothing where no document states a reading, so the
change would make about seven edges in ten stop moving — which reads as a
regression, correctly. The right sequencing is coverage first, then the retarget.

The rest of Phase 4 is uncontested and worth doing: confirming disclosure and
commercial/isolate handling still behave after layout and filter changes, and
listing unenforced validator invariants.

**One validator trap you will hit**, twice hit already: `reason: 'caveat'` and
`'resolved'` in a `_dropped` note require the named edge to **exist** — they
annotate an edge. For a mechanism that is statutory but suspended, or an
observation about a node, use `'note'`.

## 9. Conventions that are load-bearing

- **The evidence rule**: a dependency exists only if a document says so. Every edge
  carries an `evidence_url` and a `basis` quoting the document. Things believed but
  uncited go in `_dropped` with a reason, permanently. Negative findings —
  a formula that reads no published series, a body that publishes nothing
  retrievable — are first-class results and among the most-read entries.
- **Grok**: Thomas trusts Grok's *sourced* answers directly, no independent
  refetch. But a pointer is not a source. Two rounds of Grok research this week
  came back with ~40% of `evidence_url` fields as descriptions of where a document
  lives rather than URLs, and the cheap citation-resolution pass that fixed them
  caught four confident, specific errors that no plausibility check would have
  caught. Resolve placeholders; keep Grok's structure.
- **Some hosts are egress-blocked from the sandbox**, and it looks exactly like a
  JavaScript-rendering failure. If Playwright throws `ERR_CONNECTION_RESET` at
  `page.goto`, it is the network, not the page, and a rendering browser will not
  help. Confirmed blocked: `budgetservices.lausd.org`, `www.houstonisd.org`,
  `library.municode.com`. `WebFetch` sometimes reaches hosts the sandbox cannot.
- **Planning docs go stale in a specific direction**: they are most wrong about
  whatever Thomas looked at most recently. Several still describe the
  within-country contrast, the scope-panel clipping and the backwards pulses as
  open; all three were fixed on 2026-08-09. Thomas approved a reconciliation pass
  (Q20) which has not been done. Treat `planning/*.md` as evidence about the past,
  and the source code as evidence about the present.
- **Project memory** is the fastest way in. `MEMORY.md` indexes ~30 topic files.
  The ones most relevant to this review: `node-scale-legibility`,
  `dim-focus-is-not-the-lever`, `cluster-spacing-declined`,
  `open-decisions-2026-08-10`, `hollow-nodes-not-flags`,

## 10. One honest disagreement with the plan

The plan de-prioritises research expansion for 4–8 weeks, on the reasoning that
adding volume while the graph is slow and overlapping makes usability worse. That
is sound for *volume*. It is worth separating from **hub** research, which does the
opposite.

The clearest example: the African branch currently looks like seven unconnected
islands, and the measured reason is that all seven countries are non-AFRISTAT and
sit in four different regional blocs, so they share no methodological parent.
Adding AFRISTAT and the African Charter on Statistics as hub nodes would *reduce*
apparent hairball by giving a whole region a spine — three or four nodes that make
seventy legible. Thomas already approved that specific work (Q17).

So: freeze breadth, but do not freeze the handful of hub nodes that make existing
breadth readable. That is a legibility task wearing a research task's clothes.
