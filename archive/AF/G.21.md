## Secondary observations

* **A real git-tooling issue on this device, worked around, worth remembering for future sessions:** every `git` command invoked via `device_bash` in this repo — even a plain `git status` — creates `.git/index.lock` (and, for write operations, `.git/objects/**/tmp_obj_*` temp files) and then emits a `warning: unable to unlink '...' — Operation not permitted` when it tries to clean up after itself. This is the same "device_bash cannot delete files" mount restriction documented generally for this bridge, just surfacing through git's own internal lock/temp-file cleanup rather than through an explicit `rm`. Read commands (`status`, `log`, `diff`) appear to complete correctly despite the warning — the warning fires only at cleanup, after the actual read already succeeded. Write commands (`git add`) also appear to complete correctly (confirmed via `git status` afterward showing the expected staged state) despite leaving `tmp_obj_*` litter behind — but a STALE `.git/index.lock` left over from a previous command's failed cleanup will make the NEXT git command fail outright ("File exists"), since `device_bash` can't `rm` it, only `mv`. The workaround used throughout this session: before every git command that follows another git command, `mv .git/index.lock _to_delete/stale-index-lock-N` first (ignoring "No such file" if there's nothing to move). This adds an extra round-trip per git command but is fully reliable. A future session doing heavier git work in this repo should budget for this, and could consider periodically `mv`-ing the accumulated `.git/objects/**/tmp_obj_*` litter into `_to_delete/` too, though this session did not observe any actual corruption or missing-object errors from leaving them in place (git added the real content successfully regardless).
* **The tar-and-stage validate route (`npm-validate-procedure` memory) continues to be the only reliable way to run this repo's own `validate`/`build` scripts** — confirmed again this round, `device_bash` still fails outright on `tsx`/`esbuild` (`@esbuild/win32-x64` vs the Linux VM) exactly as documented.
* **Grok's per-item confidence framing was a reasonably good predictor of what would independently verify**, this round: the 2 items Grok itself flagged as high-value URL+quote leads (CI, BF) both substantively checked out; the 1 item that was itself an inference-from-silence (Angola elections) needed, and got, independent strengthening rather than a straight accept-or-reject; and the koulouba.ml item, despite Grok supplying a rich, specific-sounding quote, turned out to be built on a source this session could not access at all — a reminder that quote specificity is not itself evidence of access, since Grok's own tooling may reach sites this branch's own fetchers cannot (or vice versa).
