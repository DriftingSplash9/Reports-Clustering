## 1. What this session built: collapsible-orb drilldown

Thomas's brief: as the corpus grows past ~1000-1200 nodes, load the graph fully
collapsed into one "orb" per political/administrative family (Canada, US, EU,
etc.), and let double-click progressively unfold each family's own level ladder
(federal → provincial → municipal → institutional, or the equivalent per family)
into real individual nodes — a "protein unfolding" feel, with position continuity
across each toggle rather than a re-scatter. Locked-in design decisions from
earlier in the process: draw all edges when collapsed, no merging/aggregation;
double-click opens AND closes (symmetric gesture); fully collapsed is the default
load state.

**The model** (`src/lib/hierarchy.ts`): `Drilldown = Partial<Record<ColourFamily,
number>>` — one number per family, meaning "how many rungs of this family's own
ladder have been peeled into real nodes." Absent/0 = fully collapsed. The ladder
itself is `SCOPE_GROUPS` in `palette.ts`, reused rather than duplicated.

**This is the fact that matters most for §3 below: it is one number per family,
not a tree.** There is no per-branch state at all. Opening a family's next rung
reveals *every* real node at that rung, across the whole family, in one flat list
— not the children of whichever specific node you clicked. `orb:CA` stands for
"everything in Canada not yet peeled off," not "everything under this specific
node." There is exactly one orb per family, always, never one per branch.

**`buildDisclosedGraph(graph, drilldown)`** resolves every real node to
itself-or-its-family-orb, groups collapsed members into one `OrbNode` per family,
remaps every edge to whichever id each endpoint currently resolves to (dropping
only true self-loops), and recomputes in/out degree over that remapped edge set.
Edges are never merged — two real edges that both end up orb-to-orb stay two
separate lines.

**`toggleDrilldown(current, id, report?)`** (`hierarchy.ts:225`):
- Double-click an orb → `drilldown[family] = min(depth + 1, ladder.length)`. Opens
  exactly one rung.
- Double-click a real node → `drilldown[family] = idx` where `idx` is that node's
  own ladder index. Folds that rung and everything narrower back into the orb.

**Also fixed this pass, upstream data bugs found while building the ladder:**
`SCOPE_GROUPS` in `palette.ts` was missing `'US:municipal'` (33 reports) and
`'INT:supranational'` (3 reports) from their family's ladder arrays, despite valid
`SCOPE_COLOUR`/`SCOPE_LABEL` entries existing for both — meaning those 36 reports
could never collapse, and were also invisible in the pre-existing legend/filter
sidebar (unrelated bug, same root cause). Fixed by adding both to their ladder in
the correct position. Verified via a standalone script comparing every report's
`scopeOf()` against its family's ladder: 36 outliers before, 0 after.

## 2. Bugs found and fixed *before* Thomas's "terribly buggy" report

These were all found and fixed via headless-Chromium testing against the actual
Vite **dev server** (`npm run dev`, port 5173, React Strict Mode on) — not the
production `vite build`/`vite preview` pipeline, which is what earlier testing in
this session used and which did **not** reproduce any of them. That gap mattered:
Strict Mode's dev-only behavior and the production build are different enough
pipelines that a clean pass on one says very little about the other. **Test
against `npm run dev` specifically from here on**, matching Thomas's own setup.

**Kapsule async-digest tick race** (pre-existing, not new this pass): three-forcegraph
batches chained setters into an async digest; a freshly rebuilt `forceGraph` (which
now happens on every drilldown toggle, not just once at mount) can get
`tickFrame()`'d before that digest finishes, throwing `Cannot read properties of
undefined (reading 'tick')`. Fixed with a try/catch around `ref.current?.tickFrame()`
in `useFrame` (`InfluenceGraph.tsx` around line 1195) that silently skips one frame.
**This mostly still holds**, but see §3 — I now suspect this same try/catch may be
masking something else in certain states, and it's worth a harder look; I did not
find a case where it fires repeatedly rather than once, but I also did not try very
hard once the bigger bug (§3) explained what I was seeing.

**Violent re-explosion on opening a large family.** Newly-revealed real nodes were
all seeded at the *exact same point* — their family orb's last known position
(`InfluenceGraph.tsx`, the `forceGraph` useMemo, node-seeding logic). Charge
repulsion between exactly-coincident nodes is degenerate; d3-force-3d flings them
apart hard, and for a large family (EU has 73 supranational reports) this sent the
whole connected cloud flying far outside the camera's frame for several real
seconds before the fit caught up — with **zero console errors**, because nothing
was actually broken, the camera was just aimed at a stale small-radius guess while
the true cloud kept growing past it. This read, to someone watching it happen
without knowing the internals, as "I double-click and everything disappears" —
which is close to verbatim what Thomas reported before this fix shipped.

Two changes, both still in the shipped code:
1. **Jitter.** `InfluenceGraph.tsx:473-474`, `SEED_JITTER = 14`: each newly-seeded
   real node gets a small random offset from its parent orb's position instead of
   landing exactly on it, breaking the degenerate co-location up front.
2. **Continuous tracking re-fit.** `InfluenceGraph.tsx:144-145`,
   `REFIT_INTERVAL_SECONDS = 0.2`, `REFIT_WINDOW_SECONDS = 12`. Previously the
   camera only fit twice per rebuild — once early (`MIN_TICKS_BEFORE_FIRST_PAINT`,
   line 112) and once on `onEngineStop` (which, measured, can fire *while the
   cloud is still visibly moving* — it's gated on alpha decay, not on actual
   stillness). Now, once the early fit lands, `runFit()` is called again every
   `REFIT_INTERVAL_SECONDS` of **wall-clock** time (via `useFrame`'s `delta`, not
   a tick count — a tick is not a fixed amount of real time, and timing this in
   ticks was tried first and was wrong for exactly that reason, see the comment
   at `InfluenceGraph.tsx:123-145` for the full reasoning) for up to
   `REFIT_WINDOW_SECONDS` after every rebuild.

**This is very likely the direct cause of §3's camera-snapping complaint — read
that section before touching this code.**

**Isolated-nodes shelf moved out of the 3D scene.** Previously (`shelveIsolated`,
now deleted) isolated reports (no edges in either direction — 85 of 728 currently)
were rendered as real, pinned nodes in a world-space column beside the connected
cloud. A world-space position, pinned or not, still turns with the camera —
dragging or auto-orbiting swings that column around the graph like everything
else, which Thomas flagged as distracting ("I don't like them just spinning
around the cluster"). Fixed by excluding isolated real nodes from the 3D graph
entirely (filter in the `forceGraph` useMemo's node construction,
`InfluenceGraph.tsx`, right before the seeding logic) and rendering them instead
as a genuine screen-space HTML overlay — `IsolatedShelf` in `App.tsx:1120`, a
fixed panel between the search bar and the View panel, 4 dots wide
(`isolatedShelfGrid` style const), hover shows the normal detail tooltip, click
selects (toggles) via `handleSelectIsolated` (`App.tsx:337`). This list is
deliberately computed off the whole-corpus `graph`, not `disclosedGraph` — see the
comment on `isolated` at `App.tsx:441` for why isolation is orthogonal to the
drilldown ladder and shouldn't fold with it.

One consequence worth knowing: `selected` in `App.tsx` (used by the left Hud panel)
now falls back from `disclosedGraph.byId` to `graph.byId` (`App.tsx` around line
215), because an isolated node selected from the shelf may not have its own entry
in the disclosed view if its family hasn't been drilled that far open yet — without
the fallback, selecting a shelved node silently showed no "Tracing" info.

**Minor: duplicate React key warning.** `ListBlock` in `App.tsx` (the "Feeds
into"/"Built from" lists on the hover card) keyed rows by `item.text` (the
neighbour's title). `dependents`/`dependsOn` in `graph.ts` return one entry **per
edge**, not per neighbour, and an orb collapsing several distinct real edges into
one orb-to-orb pair (by design — edges aren't merged) means the same title can
legitimately repeat. Harmless but constant console noise on hovering any busy
orb. Fixed by keying on array index instead — the displayed content is unchanged,
only the React key.

All of the above passed: `tsc --noEmit`, `npm run build`, `npm run validate`, and
repeated headless-browser passes (open several orbs, repeated double-click,
Reset, drag-orbit, toggle auto-orbit) with zero console/page errors. **None of
that caught what Thomas is now reporting** — see §3 for why, and take it as a
caution about what this kind of testing does and doesn't prove.

## 3. What Thomas reported just now, verbatim, and my diagnosis

> "this is terribly buggy, sometimes when i move the camera it snaps back, when i
> scroll to zoom it snaps back to fit, when I double click the Top level node I
> want all of the nodes at that level and the level below opened. We have our
> first view of the supranationals, then we have the national views, then the
> state/province levels, then the municipal level last. If one province is double
> clicked then the whole network will open. then when the country is double
> clicked ALL provinces and states come into play."

This is at least two, possibly three, separate issues. Splitting them out:

### 3a. Camera snaps back on manual drag / scroll-zoom — almost certainly my regression

**High confidence, start here.** The continuous tracking re-fit added in §2
(`REFIT_WINDOW_SECONDS = 12`, re-fitting every 0.2s) calls `runFit()`, which does
`camera.position.set(...)` and `orbit.target.copy(...)` unconditionally
(`InfluenceGraph.tsx:876, 886`) — it has no way to know the user just dragged or
scrolled, and will overwrite whatever they just did on the very next 0.2s tick.
For up to 12 real seconds after **every single drilldown toggle**, any manual
camera input is fighting a timer that wins every fifth of a second. Someone
actively exploring the graph (which is exactly what triggers this feature) is
essentially always inside that 12-second window, which would read as constant,
maddening snap-back — matching "sometimes... snaps back" and "scroll to zoom...
snaps back to fit" almost exactly. `runFit()` explicitly sets the camera to the
*fitted* distance (`InfluenceGraph.tsx:876`), which is precisely "snaps back to
fit" if it fires while someone's mid-scroll.

The old code (before this session) only fit twice per rebuild — once early, once
on `onEngineStop` — so this failure mode existed in miniature before (a user
unlucky enough to drag in a narrow window could get one snap), but it was rare
enough that testing this session never hit it. Widening that from "twice, ever"
to "every 0.2s for 12 seconds" was the trade I made to fix the explosion in §2,
and I did not go back and re-test manual camera interaction *during* that window
before shipping — that's the gap. **I got this wrong and didn't catch it before
Thomas did.**

This needs a real fix, not just reverting the window (reverting brings the
explosion bug back). The right shape is probably: track whether the user has
touched the camera (OrbitControls exposes a `start`/`change`/`end` event, or you
can diff `camera.position`/`orbit.target` against what `runFit()` last set) and
skip the periodic re-fit — or shrink the window drastically — the moment that's
true, resuming only on the *next* toggle. I did not implement this; I'm flagging
the shape of it because I ran out of runway on this pass, not because I've ruled
it out.

**Start by reproducing this cleanly**: open a couple of orbs against `npm run
dev`, then immediately try to drag-orbit and scroll-zoom repeatedly over the next
10-15 seconds, and confirm the snap-back happens on that cadence (roughly every
0.2s of no interaction, or overriding an in-progress one). If confirmed, the fix
is almost certainly in `InfluenceGraph.tsx`'s `useFrame`, around lines 1170-1185
(the periodic-refit branch) and/or `runFit()` itself (line 814) needing a "has the
user touched the camera since the last fit" guard.

### 3b. Double-click should open two rungs at once, at least from the top

> "when I double click the Top level node I want all of the nodes at that level
> and the level below opened"

Read plainly: double-clicking a fully-collapsed family orb (depth 0) should jump
straight to depth 2 (open both the first rung *and* the one under it), not just
depth 1 as it does now. This is a small, well-scoped change if that's really all
he means: `toggleDrilldown`'s orb branch (`hierarchy.ts:225-231`) changes from
`Math.min(depth + 1, ladder.length)` to `Math.min(depth + 2, ladder.length)` —
**but confirm with Thomas whether this applies to every orb-click at every depth,
or specifically/only to the first click on a fully-collapsed top-level orb.**
"the Top level node" suggests the latter (only the family orb before anything is
open), which would need the +1-vs-+2 choice to depend on whether `depth === 0` at
the time of the click, not a flat change to the ladder-advance amount everywhere.
Ask before guessing — a flat +2 everywhere changes the feel of drilling through
every remaining rung too, not just the first one, and he described the sequence
(supranational → national → province → municipal) like a tour he wants to move
through, not just a faster first step.

### 3c. "The whole network opens" / "all provinces and states come into play" — likely describing the flat-ladder architecture, not a bug

> "If one province is double clicked then the whole network will open. then when
> the country is double clicked ALL provinces and states come into play."

Re-read against §1's "one number per family, not a tree": **this is very likely
exactly what the current design does on purpose**, and Thomas is discovering that
live rather than reporting a defect. Opening a family's next rung is, by
construction, all-or-nothing across the whole family — there is no per-province
orb, so double-clicking to open "under" one province necessarily reveals every
province (there's only one shared next-rung reveal per family), and there is no
mechanism to open *only* Alberta's municipalities without also exposing every
other province's.

Two readings of his message, and they lead to very different amounts of work:

1. **He's describing current behavior neutrally, as context for 3b** (i.e., "here
   is the ladder order, and here's what currently happens when you open things,
   which is why I want the first click to skip ahead"). If so, no architecture
   change needed — just resolve 3b.
2. **He's objecting to the flat reveal** and actually wants a real tree: click a
   province, get *only* that province's municipalities, with other provinces
   staying collapsed. If so, this is a genuine re-architecture — `Drilldown`
   would need to move from "one depth number per family" to something tracking
   expansion **per node/branch** (e.g. a `Set<string>` of expanded real-node ids,
   with orbs keyed per-branch rather than per-family — `orbId` would need to
   become a function of the expanded ancestor, not just the family). That
   touches `hierarchy.ts` almost completely (`resolveId`, `buildOrbNode`,
   `buildDisclosedGraph`, `toggleDrilldown` all assume one-orb-per-family right
   now) and has ripple effects into the position-seeding logic in
   `InfluenceGraph.tsx` (`lastPositions`, keyed off ids that would no longer be
   stable in the same way).

**Do not build #2 on a guess.** Ask Thomas directly which of these he means
before writing code — the cost of guessing wrong is a substantial rewrite of the
core data model for nothing. A reasonable way to surface the question: describe
the current flat-per-family behavior back to him in plain terms ("right now,
opening one level shows *everyone* at that level across the whole country, not
just the branch you clicked — is that what you want changed, or is the only
complaint that the first click should jump two levels?") and let his answer
decide whether this is a small change (3b only) or a big one (a real tree).

## 5. Testing method notes (reusable, and where it still fell short)

- Chromium at `/opt/pw-browsers/chromium`, install `playwright` in `/tmp` not the
  repo, launch with `--use-gl=swiftshader --enable-webgl --ignore-gpu-blocklist`.
- **Test against `npm run dev` (port 5173, Strict Mode on), not `vite
  build`/`vite preview`.** This session's earlier rounds tested only the
  production pipeline and it did not reproduce the bug Thomas hit; switching to
  the dev server is what found the real explosion/camera-tracking issue in §2.
- To click precisely: a temporary `window.__debugIG = { forceGraph, camera }`
  hook dropped into `useFrame`, plus an in-page reimplementation of
  `Vector3.project()` (via `camera.matrixWorldInverse`/`projectionMatrix`,
  reading `Matrix4.elements` in column-major order) to compute exact screen
  coordinates from real node world positions *within the same page session*
  being clicked — d3-force-3d randomises layout per page load, so coordinates
  guessed from a screenshot taken in a different session are close to random.
  **Remove this hook before shipping** — it was in the code at points this
  session and was stripped each time before delivery; grep for `__debugIG`
  before calling anything done.
- This sandbox's software-rendered (SwiftShader) WebGL is dramatically slower
  than real hardware — observed as low as ~2.7 simulation ticks/second on the
  full 728-node scene with bloom on, versus a real GPU's 60fps. Timing-sensitive
  bugs (like §2's explosion, and probably §3a) look far more extreme here than
  they will on Thomas's actual machine, and things that "eventually recover" in
  15+ seconds here may recover in under a second for him — **but the underlying
  bug is still real**, just compressed in time. Don't use this sandbox's wall-clock
  numbers as a proxy for what Thomas experiences; use it to confirm a bug exists
  and roughly bound it, then trust his live report over your own timing.
- Native browser double-click-streak detection: rapid same-pixel `dblclick()`
  calls in immediate succession only fire the `dblclick` event on the first one;
  later ones in the same streak only fire `click`. This is a Playwright/browser
  testing artifact, not an app bug — space out synthetic double-clicks or
  re-verify with a fresh pointer position each time.
